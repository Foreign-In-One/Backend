# TaxCheck 1차 구현 — 합의한 규칙과 인수인계

결정일: 2026-09-01. 관련 이슈: Backend #5. 기준 브랜치: `feature/taxcheck#5`.
기준 원격 커밋: `9605956288204ab5bfd89a32b25d7616c579eab1`.

## 이번 대화에서 확정한 개발 규칙

사용자 승인: 사용자 입력·확인 방식으로 입력 명세를 정하고 구현한다. 반복 확인 대신 구현 후 동작과 한계를 설명한다.

1. 실입금 합계와 세금 계산용 소득을 분리한다.
2. 실입금 합계는 서버 Paycheck의 귀속월을 기준으로 해당 연도만 집계한다.
3. 세금 계산 입력은 사용자가 귀속연도 문서의 총급여와 단일세율 계산에 포함할 비과세소득을 입력·확인한다.
4. 프론트 합계, Paycheck 실수령액, 계약 기본급, OCR 성공 표시를 세금 소득의 확정값으로 대체하지 않는다.
5. 미확인 금액은 `null`이며 0과 다르다. 계산하지 못한 이유를 응답한다.
6. 19% 적용을 가정한 소득세 참고값만 제공한다. 일반세율·차액은 `null`, 자격·유불리·환급액은 확정하지 않는다.
7. 시뮬레이션은 원본 입력 스냅샷을 기준으로 결과만 반환한다. 어떤 DB 기록도 자동 저장/수정하지 않는다.
8. 실제 분석만 이력으로 저장하며, 과거 분석은 이후 Paycheck/프로필 변경으로 바뀌지 않는다.
9. LLM에 수치 계산·세무 확정 판단을 맡기지 않는다.
10. Navbar/Front·Dashboard/Records API·OCR 공급자·빌드 설정은 이번 패치 범위가 아니다.

이 파일은 다음 작업에서 다시 확인할 프로젝트 결정 기록이다. 다른 대화에 자동으로 장기 기억된다고 보장하는 대신 코드와 함께 보관한다.

## 구현한 기능

- TaxCheck 4개 endpoint, 별도 요청·응답 DTO, 공통 ApiResponse.
- 명세의 TAX_CHECK 컬럼·User/Document FK를 그대로 사용한 Entity/Repository.
- 소득 입력, 설문, 프로필 참고값, 당시 실입금 합계, 계산 버전/결과를 `benefit_summary` JSON에 스냅샷으로 저장.
- `annual_income`은 사용자가 확인한 총급여(비과세 제외); 비과세 항목은 입력 스냅샷에 보존. 기존 DB 컬럼 추가/의미 변경 없음.
- `required_documents` JSON은 `{ "items": [...] }` 형식.
- TaxCheck 전용 JSON converter로 소수 금액의 BigDecimal 정밀도를 보존. 공통 converter는 변경하지 않음.
- 사용자별 기록 필터, 문서 소유자/유형 검사, 음수·소수 자리·상한·귀속연도 검사.
- 잘못된 JSON/파라미터에 TaxCheck controller 범위의 400 응답.
- 새 TaxCheck FK 때문에 기존 개발용 시드 초기화가 실패하지 않도록 DataInitializer 삭제 순서에 TaxCheck 추가.
  실제 데이터에 시드 초기화를 실행하지 말 것. 이 작업에서는 실제 DB 초기화를 실행하지 않았다.

## 무엇을 확정하지 않는가

- 183일 참고값만으로 거주자/비거주자를 판정하지 않는다. 입국일 이후 실제 출입국/주소 이력은 확보하지 않았다.
- 주택마련저축 가입·무주택·납입증명서 3개 응답만으로 공제 가능/불가를 판정하지 않는다.
- 공제를 이용 중이라는 사실만으로 단일세율 자격을 배제하지 않는다.
- 19% 참고액 계산 성공을 `POSSIBLE` 또는 적용 승인으로 표시하지 않는다. `eligibilityConfirmed=false`다.
- 근무 전, 기록 없음, 금액 미확인, 확인된 0원은 구분한다.
- 단일세율 포함/제외 근로소득 항목, 최초 국내 근로일, 특수관계, 일용근로 여부, 전체 연도 완전성은 사용자의 자료와 추가 검토가 필요하다.
- 사용자 입력 검증은 형식·범위 검사다. 문서 진위, 허위 입력, 세법상 소득 분류의 정확성을 자동 보증하지 않는다.
- 현재 연도가 끝나지 않았다면 연중 누계액을 연간 확정 소득이라고 확인하면 안 된다. 가상 연간 소득은 시뮬레이션으로 구분한다.

## 계산 범위와 공식 근거

이 구현의 수식은 `(총급여 + 단일세율 계산에 포함할 비과세 근로소득) × 0.19`의 참고 산술만 다룬다.
소수 2자리 HALF_UP은 화면 참고값 정밀도이며 법정 신고·징수 절사 규칙이 아니다.

- [국세청 2025년 귀속 외국인 근로자 연말정산 안내, 2026-01-07](https://www.nts.go.kr/nts/na/ntt/selectNttInfo.do?bbsId=1028&mi=2201&nttSn=1347723): 19%와 일반세율 계산 구조, 비과세 항목 포함 및 공제 배제, 적용 조건을 확인.
- [조세특례제한법 제18조의2](https://www.law.go.kr/법령/조세특례제한법/제18조의2), [관세청 법령포털 2026-04-21 시행본](https://unipass.customs.go.kr/clip/index.do?lstMod=S&opnurl=%2Flworsrch%2FopenULS0101009S.do%3FlworAdmnRulNo%3D001584&pmgtDtTpNo=2026042101): 19% 규정의 공식 출처. 개별 적용 자격의 전 조건을 코드로 구현했다는 뜻은 아님.

참고 산술 제공 연도는 2025·2026으로 제한한다. 다른 과거 연도는 분석 기록/안내는 가능하나 참고액은 `null`이고 `TAX_YEAR_RULE_NOT_VERIFIED`를 반환한다. 미래 귀속연도는 입력 오류다.
향후 다른 연도 지원 시 공식 근거와 테스트를 갱신한다. 기존 저장 분석은 당시 규칙 버전을 유지한다.

## 왜 이렇게 나누었는가

일반세율의 유불리를 비교하려면 필요한 공제·기납부 항목과 규칙을 먼저 확보해야 한다.
지금 계산하지 않는 항목을 0원처럼 보여주지 않으며, 실입금 기반으로 잘못된 세금을 계산하지 않는다.
실제 분석과 가정 시나리오를 분리해 Dashboard/Records가 가정 결과를 실제 최신 기록으로 오인하지 않게 한다.
따라서 이 버전은 **자료 준비 + 19% 가정 참고 계산**이며, 완성된 절세 비교 서비스가 아니다.

## 검증 상태 (정직한 구분)

- 실제 실행: 순수 Java 규칙 소스 컴파일 및 29개 시나리오 통과(내부 27개 주택 설문 조합 포함).
- 실제 실행: 전체 Java 80개 파일 문법 파싱 검사. Spring/JPA/Lombok 타입/의존성 검사와는 다르다.
- 실제 실행: 변경 diff 공백 검사 및 기준 파일에 대한 패치 적용 검사(패키지 생성 단계).
- 작성했으나 이 환경에서 실행하지 못함: Spring/H2 API 통합 테스트 13개, JSON converter JUnit 테스트 3개, Gradle 전체 회귀 테스트.
- 이 환경에는 Java 17 실행 환경만 있고 프로젝트는 Java 21을 요구한다. 외부 Gradle/Maven 다운로드도 승인되지 않아 전체 빌드·테스트를 완료했다고 주장하지 않는다.
- MySQL 실환경 FK/JSON 동작, 실제 브라우저/프론트 연결, 실제 서버 기동은 아직 확인하지 않았다.

Java 21 IntelliJ 환경에서 아래를 통과시키고 실패하면 먼저 수정한다.

```powershell
.\gradlew.bat test --tests '*TaxCheck*'
.\gradlew.bat test
```

테스트는 `src/test/resources/application.yml`의 H2 테스트 DB에서 실행한다. `bootRun`이나 개발용 시드 초기화 API를 테스트 대신 사용하지 않는다.

합의한 방향 안의 구현 세부 사항은 진행하고, 공통 API/DB 의미·외부 공급자·실제 법률 판정 등 범위를 바꿔야 할 때만 다시 확인한다.
